  in every input class; error prints remain unconditional
- DHT11 now publishes humidity alongside temperature using an `auxiliary` field:
  `{ "value": temp, "auxiliary": { "humidity": humidity } }`

### Phase 3.2 — Design Fix: Temperature vs Humidity Effect Assignment
- Documentation-only. No firmware changes.
- Identified that temperature changes too slowly (10–30s) for a real-time game mechanic;
  humidity changes in 2–3s and is better suited for dynamic effects
- Swap is handled in ASP.NET server and Unity — firmware publishes both values unchanged

### DHT11 slotId Fix
- `slotId` was `"temp"` — a semantic data label, violating the Phase 2.1 rule that
  slotId must be a physical hardware identifier
- Renamed to `"dht11"` across `config.py`, `config.example.py`, and `CLAUDE.md`

### ESP32-32U Pinout Research
- Confirmed ESP32-32U = WROOM-32U (external U.FL antenna, identical GPIO map to WROOM-32D)
- Key finding: **ADC2 is unusable while WiFi is active** — MicroPython raises an exception
- Safe ADC pins (ADC1 only): GPIO 32, 33 (full I/O), 34, 35, 36, 39 (input-only)
- Joystick axes must use ADC1 pins — 32 and 33 are the best choice (support pull-up)
- Hard-avoid: GPIO 6–11 (internal flash), 1 and 3 (UART/REPL)
- Boot-sensitive: GPIO 0, 2, 5, 12, 15 — avoid for button inputs

## Problems Faced

### 1. DHT11 slotId carried semantic meaning
`"temp"` described the data, not the hardware. After Phase 3.1 added humidity to the
same slot, the name became actively wrong — the slot now carries two values.
**Fix:** renamed to `"dht11"` everywhere.

### 2. Debug prints flooded the REPL
`tick()` runs every 10ms. Unconditional prints on every sensor change made the serial
monitor unreadable and wasted RAM on string formatting in the hot loop.
**Fix:** `DEBUG` flag in `config.py`; all emit/raw-read prints gated behind `if DEBUG:`.

### 3. DHT11 humidity was discarded
Phase 3 spec said temperature only. But DHT11 produces both from a single hardware read —
discarding humidity wasted real data and forced a second sensor if humidity was ever needed.
**Fix:** Phase 3.1 `auxiliary` field carries humidity alongside temperature in every event.

### 4. Temperature too slow for real-time game mechanic
Temperature in a room changes on a timescale of tens of seconds — not useful for driving
something the player feels immediately. Discovered during design review.
**Fix (Phase 3.2):** server/Unity swaps the effect assignment. Humidity (fast) drives the
dynamic mechanic; temperature (slow) drives a slower environmental effect.
